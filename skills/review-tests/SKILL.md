# Review: test coverage against real failure modes

You answer one of two questions.

**Question A — the delegated one.** Another reviewer suspects a defect and needs to know:
*does a test exist that would have caught this?* Answer it with evidence, not with a filename
guess.

**Question B — the standalone one.** Given a test suite, does it defend the things that
actually break here?

Coverage percentage answers neither. A suite at 90% line coverage shipped the most expensive
bug in the history behind `<review-kit>/PRACTICES.md`, because every test exercised one code path and
the defect was that there were three. (`T-6`, `C-4`)

## Question A: would a test have caught this?

Do not answer from filenames or from the presence of a `test_` prefix. Answer in this order,
and stop at the first step that settles it:

1. **Find the tests that touch the code in question.** Grep for the function, the module, and
   the behaviour — not just the name, since the test may exercise it through a caller.
2. **Read them.** A test that imports the function and asserts nothing about the behaviour in
   question does not cover it.
3. **Break it and see.** This is the only conclusive answer and it is usually cheap: introduce
   the defect in a scratch copy, or invert the condition, run the kit, and see whether
   anything goes red. A test that stays green against the injected defect does not cover it, no
   matter what it is named.
4. If you cannot run the kit, say so explicitly and return `speculative`. Never assert a test
   is missing without having looked. (`FINDINGS.md`, evidence)

Return: whether a test exists, which test, whether it would fire, and the command you ran.

## Question B: does the test suite defend what breaks?

### The failure modes that matter here

- [ ] **Leakage has a test.** (`T-3`) For every target-dependent transform: corrupt the
      held-out labels and assert the transform's outputs do not move. If this test does not
      exist, that is the single highest-value missing test in a repository of this kind, because
      its absence produces a beautiful score and no error.
- [ ] **One code path is asserted to be one.** (`T-5`, `C-4`) A test asserting *structurally*
      that every fit path routes through one function — not three tests each checking one path
      produces the right output. The structural assertion is the one that survives someone
      adding a fourth path.
- [ ] **Seeds reproduce.** (`T-7`) A test that runs a seeded operation twice and asserts
      identical output. Absent this, non-determinism is discovered when two numbers disagree and
      neither can be re-derived.
- [ ] **Split integrity.** A test asserting train and validation do not share entities, do not
      overlap in time where they must not, and that no row appears in both.
- [ ] **Pure helpers, hand-computed.** (`T-2`) Fixtures whose expected values were worked out by
      hand. A fixture generated by the code under test asserts only that the code has not
      changed — flag every one you find, they are common and they look like real tests.
- [ ] **Shape and schema contracts.** A test asserting row count, dtypes and index alignment
      survive a merge or a transform, rather than only checking a value.
- [ ] **Edge cases the data will actually produce.** Empty group, single-row group, all-null
      column, a category unseen at fit time, a duplicate key, a boundary timestamp at a
      daylight-saving transition.
- [ ] **Structural invariants about artefacts.** (`T-5`) That an appended log row lands where it
      belongs; that a written artefact is complete; that a config hash covers what it claims to.

### Gating

- [ ] **Gated per test, never per module.** (`T-1`) A module-level skip means a machine without
      data reports a clean run — exactly when the suite must not be green. Check for
      module-level `pytest.skip`, `pytestmark` on a whole file, and import-time guards.
- [ ] Skipped and expected-failure tests: list them with their reasons, and flag any whose
      reason has expired.
- [ ] A test suite that passes with no data available and does not say which tiers it skipped.

### Test quality

- [ ] A test with no assertion, or asserting only that nothing raised.
- [ ] An assertion so loose it cannot fail — `assert len(result) >= 0`, `assert result is not
      None` on something that could not be None.
- [ ] A tolerance wide enough to hide a real regression. Check `rtol`/`atol` against the
      magnitude of the quantity; a default tolerance on a quantity in the thousands admits a
      large error.
- [ ] A test asserting a golden value with no comment on where the value came from. (`C-5`)
- [ ] A test depending on another test's side effect, or on execution order.
- [ ] A test that hits the network, the real data, or a shared mutable path without a marker.

## Reporting

**Invoked by another reviewer:** return the answer in prose, directly. Say which test, whether
it fires, and what you ran to find out. Be brief; you are answering one question.

**Run standalone with an output path:** write JSON per `<review-kit>/FINDINGS.md`, with
`denominators` carrying tests collected and target-dependent transforms found versus leak-tested.
Print one line only.

A missing test is a finding with `fix_certainty: judgment` unless the test is a one-liner whose
content is obvious, and its `fix` names the assertion to write — not "add tests".
